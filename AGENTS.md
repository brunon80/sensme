# AGENTS.md — Engineering rules for Moodwave

Rules for every human or AI agent working in this repository. Read this fully
before making changes. When rules conflict, this file wins over habits;
`docs/TECHNICAL_DECISIONS.md` wins over re-litigating settled architecture.

## 1. Product mission

Independent, offline-first reimplementation of Sony SensMe Channels: automatic
music analysis, tone-axis classification, channel-based discovery, and a
faithful recreation of the PSP SensMe Channels experience. No Sony software,
no proprietary services, no cloud dependency.

## 2. Architecture rules

- **One core, many shells.** All domain logic (analysis, classification,
  library, persistence) lives in Rust crates under `crates/`. UI shells
  (Tauri, React Native, web) are thin: presentation and I/O only. Never
  duplicate business logic in a shell.
- **Shared contracts only.** Shells consume types from `contracts/generated/`
  (generated by `ts-rs` from Rust — never hand-edit generated files) and
  visual values from `contracts/design-tokens/`.
- **The analysis engine must be deterministic and identical across
  platforms.** Use `f32` in the analysis path. Never call platform-native
  audio DSP from the core. Golden feature-vector tests (`fixtures/`) are the
  acceptance gate for any change to `moodwave-audio` or `moodwave-classify`.
- **Versioned algorithms.** Every analysis run records
  `algorithm_version` (pipeline) and `weights_version` (classifier). Changing
  analysis semantics requires bumping the version. Never mutate a released
  version's behavior in place.
- **Classification is a pure function** of (stored feature vector, weights).
  Re-classification must never require re-decoding audio.
- **No unnecessary dependencies.** Adding a dependency requires a short
  justification in the PR/commit message. Prefer pure-Rust crates; C
  dependencies are forbidden in the analysis path and must be flagged in
  `docs/TECHNICAL_DECISIONS.md` elsewhere.
- **No microservices, no mandatory network.** Local-first, offline-always.

## 3. Engineering standards

- Strong typing everywhere; no `any` in TypeScript, no `unwrap()`/`expect()`
  on fallible external I/O paths in Rust — return `Result` with `thiserror`
  domain errors at crate boundaries.
- Every feature ships with automated tests. **Never claim a feature is
  implemented unless it has been tested.** No silent mocks or placeholders:
  if something is stubbed, say so in code (`// TODO(phase-N):`) and in the
  commit message.
- The workspace must build and tests must pass at every commit
  (`cargo check --workspace && cargo test --workspace`).
- Public crate APIs get rustdoc. Data models get doc comments stating units
  and ranges (e.g. "0.0–1.0 normalized", "Hz", "ms").
- Reproducible builds: pinned toolchain (`rust-toolchain.toml`), lockfiles
  committed, no build-time network fetches.

## 4. Benchmark discipline

- Sony reference labels are directional evidence, not ground truth. Do not
  optimize blindly to match Sony; the goal is a coherent, useful classifier.
- Any classifier change must report benchmark deltas (per-channel
  precision/recall vs. the previous weights version) using `moodwave-bench`.
- Reference datasets live in `bench/` with the format documented in
  `docs/BENCHMARK_FORMAT.md`; every dataset records its provenance.

## 5. UI/UX — Faithful Sony PSP SensMe Recreation

The user experience must be a faithful recreation of the original **Sony PSP
SensMe Channels application**, not merely an interface inspired by it.
Visual and behavioral fidelity is a core product requirement.

### Visual identity

Reproduce the original PSP experience as closely as possible:

- Original channel selection interface.
- Original channel icons and visual assets, where legally available.
- Original color palette and backgrounds.
- Original typography and visual hierarchy.
- Original music browsing experience.
- Original album artwork presentation.
- Original transitions and animations.
- Original channel navigation behavior.
- Original playback controls and interactions.

### Interaction fidelity

Preserve the original interaction philosophy:

- Channel-oriented music discovery.
- Minimalist navigation.
- Smooth transitions.
- Focus on album artwork.
- Music playback directly from channel selection.
- Consistent visual feedback.
- Nostalgic PSP-style navigation and interaction patterns.

### Reference-driven development

Do not invent a new visual identity.

Before implementing the UI:

1. Research the original SensMe Channels PSP interface.
2. Collect screenshots and visual references of every relevant screen.
3. Document screen layouts, spacing, typography, colors, icons, and transitions.
4. Identify the original interaction flows.
5. Create a visual specification based on the references.

Use the original PSP interface as the source of truth.

### Cross-platform adaptation

The application must preserve the original visual experience across Windows,
Linux, macOS, Android, iOS, and web.

Adapt input mechanisms to each platform without changing the visual identity
or interaction philosophy.

Do not redesign the application using conventional modern music-player patterns.

### Acceptance criteria

A screen is not considered complete merely because it looks attractive.
It must be evaluated against the original PSP reference for:

- Layout fidelity.
- Color accuracy.
- Typography.
- Iconography.
- Animation timing.
- Interaction behavior.
- Overall visual resemblance.

Treat visual fidelity as a first-class engineering requirement, alongside
functional correctness and music classification quality.

### Important distinction

The objective is to recreate the original application experience, not to
create a generic music player with similar colors.

Do not use Sony trademarks or copyrighted assets in a distributed product
without appropriate authorization. Use original implementations and legally
obtained references/assets.

## 6. UI fidelity workflow (operational appendix to §5)

- **Spec before code.** No screen may be implemented before its spec exists
  in `docs/UI_SPEC.md`, and the spec must cite the reference files in
  `docs/UI_REFERENCES/` it is derived from.
- **Fidelity gate.** A screen is done only when its fidelity checklist in
  `docs/UI_SPEC.md` (layout, color, typography, icons, animation timing,
  behavior) is completed and reviewed against the references.
- **Design tokens are law.** Colors, spacing, type scale, easing curves and
  durations come from `contracts/design-tokens/` — never hardcode ad-hoc
  visual values in app code.
- **No modern-player drift.** Reject changes that substitute conventional
  music-app patterns (sidebars, infinite feeds, card grids "because modern")
  for PSP-style channel navigation.
- **Input adaptation, not redesign.** Map platform input (keyboard,
  controller, touch) onto PSP navigation semantics; keep the visual model
  identical.

## 7. IP and asset rules (hard rules)

- Never commit or ship Sony assets: icons, fonts, backgrounds, logos, the
  "SensMe" name in product branding. "SensMe" may appear only in nominative
  descriptive text ("inspired by Sony's SensMe").
- Sony screens may be studied as references; shipped assets are clean-room
  reimplementations. Every recreated asset records its reference source in
  `docs/UI_REFERENCES/PROVENANCE.md`.
- Colors, layouts and interaction concepts may be reproduced; copied files
  may not.

## 8. Environment notes (current dev machine)

- Linux (WSL2). Rust pinned by `rust-toolchain.toml`.
- Requires: `build-essential` + `pkg-config` (C toolchain for linking and
  bundled SQLite), Node ≥ 22 + pnpm ≥ 9.
- Android (Phase 5): NDK + `cargo-ndk`. iOS: macOS CI only.
